# MemoryPilot 开发文档

版本：v1.0 · 调研日期：2026-10-24（北京时间）

项目：具备时序记忆的跨会话任务助理，以多人行程规划作为演示场景。

配套材料：[开源调研与选型](MemoryPilot-开源调研与选型.md) · [代码与软件包调研快照](research-snapshot.json)

本文按单人开发、熟悉基本 Python、优先在普通电脑上开发来安排，建议预留 5～6 周，每周约 15～20 小时。这是排期估算；模型额度、机器速度和上游兼容情况会影响进度。

**执行状态：本文已经核对上游代码、公开文档、软件包版本与数据来源；没有安装整套应用、调用付费模型或运行项目评测。这里的版本是候选版本，不能当成已经联调通过的依赖组合。**

文中标为“现有”的是上游已有内容；“待开发”的是你需要补上的内容。本文新增的应用脚本、测试与配置文件，均是要在开发阶段实现的项目约定，不能在空仓库中直接运行。

## 1. 做成什么样

用户分多次提出要求，系统能够记住有效信息、处理变更，并据此完成任务。回答里能查看依据，失败时能找到具体原因。

例如下面这段自建中文演示：

| 会话 | 用户输入 | 预期行为 |
|---|---|---|
| 1 | 我和小王去旅行，住宿每晚不超过 500 元；我不吃海鲜 | 建立本次旅行的约束，生成初版计划 |
| 2 | 住宿预算改为每晚 700 元，其他要求不变 | 更新本次旅行预算，保留原预算的历史 |
| 3 | 小李加入，他吃素 | 为小李记录个人要求，调整共同用餐安排 |
| 4 | 明天改去博物馆，其余安排保留 | 只修改相关部分，并检查其他约束 |
| 5 | 我们最开始的住宿预算是多少，后来为什么变了？ | 找到原始消息，按时间说明变化 |
| 6 | 给我推荐我去年最喜欢的酒店 | 如果历史没有相关信息，明确说明不知道 |

上述中文案例属于自建演示，不能算成公开数据集的原始任务。

第一版交付五项成果：

1. 一个可交互的多会话演示。
2. 一套能保存、更新、检索和追溯的记忆模块。
3. 一套决定“本次给模型看什么”的上下文组装模块。
4. 一条可重复运行的评测流程。
5. 一份有对照实验、成本统计和失败分析的报告。

第一版范围是生成和修改计划、保存本地状态。真实订票、支付、用户账号体系、多角色协作和模型训练放在以后；这些工作会分散对记忆与评测的投入。

## 2. 复用哪些开源项目

选择标准是：代码能读懂、公开授权明确、有可参考的测试或实验、近期仍能使用、与你的目标直接相关。维护日期只说明活跃度，不能代替质量验证。

| 项目 | 借用什么 | 在本项目中的定位 |
|---|---|---|
| [LangGraph ReAct 模板](https://github.com/langchain-ai/react-agent) | 现有目录、模型调用、工具循环、配置与测试结构 | **主仓库起点** |
| [LangMem](https://github.com/langchain-ai/langmem) | 从对话抽取信息、生成摘要的工具 | **主线组件**，避免从头写抽取器 |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 执行流程和中断恢复 | **主线组件** |
| [TravelPlanner](https://github.com/OSU-NLP-Group/TravelPlanner) | 本地旅行查询工具及约束检查思路 | **业务工具参考**，保留来源与授权 |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 记忆任务、证据标注与评分提示词 | **记忆质量主评测** |
| [MemoryArena](https://github.com/ZexueHe/MemoryArena) | 多人行程任务、原始运行和评分流程 | **后期端到端复现** |
| [Mem0](https://github.com/mem0ai/mem0) | 现成的记忆写入与搜索 | **外部对照组** |
| [Hindsight](https://github.com/vectorize-io/hindsight) | 保存、检索和综合记忆的完整系统 | **第二个外部对照，时间足够再接** |

主线选择是：**模板 + LangMem + PostgreSQL + 本地文本检索模型**。你自己开发的部分集中在时间版本、来源追溯、上下文选择和实验控制。

LangMem 生成候选信息，你的程序决定是否接受、如何保存版本。不要同时让 LangMem、Mem0 和自己的数据库都独立修改同一份正式记忆；Mem0、Hindsight 分别在独立实验中使用。

上游记忆示例里的 `InMemoryStore` 把内容存在进程内，重启会丢失。正式演示应换成数据库。LangGraph 的检查点保存当前会话进度，跨会话记忆另行保存，两者职责不同。[LangMem 说明](https://github.com/langchain-ai/langmem)、[LangGraph 存储说明](https://reference.langchain.com/python/langgraph/store)

完整的候选比较、固定代码版本和排除原因见配套《开源调研与选型》。

## 3. 最近的技术，哪些值得用

这里的“最近”指截至调研日期已经公开、与本任务有关的方案；不是要求把所有新组件放进项目。

| 技术方向 | 通俗解释 | 采用方式 |
|---|---|---|
| 有状态执行 | 每一步完成后留存进度，中断后可以接着跑 | 使用 LangGraph 检查点 |
| 结构化记忆 | 把一句话整理为人物、事项、数值、时间等字段 | 复用 LangMem，增加自己的校验 |
| 带时间的事实 | 分清现在有效的信息和过去曾经有效的信息 | 开发版本记录，参考 Graphiti 的时序设计 |
| 关键词与语义联合检索 | 同时按字词匹配和按意思查找 | 先单独跑两种检索，再尝试合并 |
| 按需读取原文 | 默认只给短片段，需要时再展开 | 每段摘要、事实都带原文编号 |
| 按预算选上下文 | 给模型看的内容控制在预设长度内 | 自己实现选择规则并做对比实验 |
| 完整记忆系统 | 用现成产品的能力作参照 | 独立接入 Mem0；可选 Hindsight |
| 执行经验记忆 | 记住过去什么操作有效、哪里会出错 | 第二阶段考虑，不影响第一版完成 |

已调研的 [Deep Agents](https://github.com/langchain-ai/deepagents) 自带长对话压缩、文件式记忆和更多执行能力。第一版主线使用较小的模板，方便单独控制上下文策略；第二阶段可以将 Deep Agents 作为另一种运行方式，先关闭或记录它自带的压缩行为，避免对比条件不一致。

[Graphiti](https://github.com/getzep/graphiti) 适合关系与时间变化丰富的数据。第一版的预算、偏好、行程版本用普通数据库就能表达，因此先借鉴设计，不引入额外的图数据库。

文本检索候选采用 [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)，通过 Sentence Transformers（运行文本检索模型的 Python 库）调用。“Embedding”就是把文字转换成一组可比较的数字，用来找意思相近的内容。它是已公开的轻量文本方案，并非宣称当前最新或最强。若以后处理截图，再评估 2026 年公开的 [Qwen3-VL-Embedding](https://huggingface.co/Qwen/Qwen3-VL-Embedding-2B)，第一版无需为图片模型增加负担。

## 4. 开发前先统一几个说法

| 名词 | 本文里的意思 |
|---|---|
| Agent | 能根据任务选择并调用工具的程序 |
| 上下文 | 本次模型调用能看到的消息、记忆、工具说明等内容 |
| 长期记忆 | 会话结束、程序重启后仍保存的信息 |
| RAG | 回答前先从资料或记忆里查相关内容 |
| 检查点 | 当前流程进度的存档 |
| 基线 | 用于比较的简单方案，例如只看最近几轮对话 |
| 消融实验 | 关掉一个功能，观察它究竟有没有帮助 |
| token | 模型计算文本长度的单位，不等同于一个汉字或单词 |
| 评分模型 | 按规则检查另一个模型答案的模型，仍可能判断错误 |
| P95 延迟 | 把响应时间从短到长排列，95% 的请求不超过这个时间 |

用到新概念时先解释，再写实现方式。代码标识符保留英文，方便查官方文档。

## 5. 搭建：先复现起点，再增加组件

### 5.1 环境与模型

建议 Python 3.11、Git、uv 和 Docker。uv 用于管理 Python 依赖；Docker 用于运行数据库。模型推理可以使用已有服务，不要求第一天就在电脑上运行大模型。

机器资源建议属于开发估算：16 GB 内存可先做接口模型调用与小样本实验；本地运行文本检索模型、数据库和界面时需实际观察内存。资源紧张时按顺序运行索引和评测，不同时启动所有对照系统。

生成模型先选一个你能稳定访问、支持工具调用和结构化输出的模型。若希望全本地，可以从公开的 [Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B) 等适当尺寸模型开始，但需按实际内存选择运行工具与量化版本；本文不承诺其在你的设备上达到固定速度。

开发时允许更换模型；正式对照实验必须固定模型版本、生成参数及接口地址。兼容某种接口格式，不代表工具调用和输出格式一定相同，先用小测试验证。

### 5.2 从官方模板开始

以下操作在你准备好的开发目录中执行。它们获取并固定已核对的模板代码，不会自动完成后续模块。

```bash
git clone https://github.com/langchain-ai/react-agent.git memorypilot
cd memorypilot
git checkout -b memorypilot-dev 5c15518f0f08fbd97b1c8b6437db6656e3920229
cp .env.example .env
uv python install 3.11
uv python pin 3.11
uv sync
```

若尚未安装 uv，按 [uv 官方安装说明](https://docs.astral.sh/uv/getting-started/installation/) 安装后再继续。

模板自带的开发依赖可能要求更新版本的软件包。第一次 `uv sync` 如果报依赖或网络错误，保留错误日志，按报错定位；不要连续升级整个环境。

先检查以下现有文件：

| 文件 | 先弄懂什么 |
|---|---|
| `src/react_agent/graph.py` | 模型调用与工具调用怎样循环 |
| `src/react_agent/tools.py` | 工具在哪里注册 |
| `src/react_agent/context.py` | 模型和运行配置从哪里来 |
| `src/react_agent/state.py` | 一次会话保存什么 |
| `src/react_agent/utils.py` | 模型名称如何转换为实际客户端 |
| `tests/` | 上游测试怎样组织 |

该快照的模型配置是 `provider/model-name`，例如前半段表示模型提供方。不要照搬其他教程中的冒号格式；以本项目的加载函数为准。上游 README 有遗留描述，源码中的 `Context` 和 `load_chat_model` 更可靠。[已核对的加载函数](https://github.com/langchain-ai/react-agent/blob/5c15518f0f08fbd97b1c8b6437db6656e3920229/src/react_agent/utils.py)

模板的默认工具包含网络搜索。第一步在 `tools.py` 中改为一个确定结果的本地工具，例如输入城市代码返回固定测试记录，并通过 `MODEL` 环境配置选择模型。这样首次运行只依赖生成模型，不额外依赖搜索服务。

**验收：能用一个本地工具完成一次请求；保存工具参数、返回结果和最终回答。** 模型能聊天不等于工具调用已经接通。

### 5.4 启动一个数据库

将下面内容保存为项目根目录的 `compose.yaml`，再运行命令。这里只是本地开发配置，密码是示例值。

```yaml
services:
  db:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_USER: memorypilot
      POSTGRES_PASSWORD: memorypilot_dev_only
      POSTGRES_DB: memorypilot
    ports:
      - '127.0.0.1:5432:5432'
    volumes:
      - memorypilot_pg:/var/lib/postgresql/data
volumes:
  memorypilot_pg:
```

```bash
docker compose up -d db
docker compose exec db pg_isready -U memorypilot -d memorypilot
docker compose exec db psql -U memorypilot -d memorypilot -c 'CREATE EXTENSION IF NOT EXISTS vector;'
docker image inspect pgvector/pgvector:pg17 --format '{{json .RepoDigests}}'
```

记录最后一条命令返回的镜像摘要，联调通过后把镜像固定到该摘要。摘要相当于镜像内容的编号，避免同一个标签以后指向不同内容。

在 `.env` 中增加数据库连接，以及已选模型的必要配置。示例：

```dotenv
DATABASE_URL=postgresql://memorypilot:memorypilot_dev_only@localhost:5432/memorypilot
MODEL=provider/exact-model-id
LANGSMITH_TRACING=false
```

`MODEL` 的值需要替换。接口凭据按模型提供方的集成方式配置，不能把占位符当成真实模型名称。`.env` 不提交到代码仓库。

首次初始化要分别处理 LangGraph 库自己的表和你的业务表。PostgreSQL 存储需要调用其 `setup()` 创建表；启用语义检索时还需要配置检索模型和向量维度。[官方存储参考](https://reference.langchain.com/python/langgraph/store.postgres/base/PostgresStore)

文本检索还需要一个小适配函数：输入一组文字，输出对应的数字向量，再交给 Store 使用。Qwen3-Embedding-0.6B 默认维度为 1024；按官方示例分别处理查询提示与被检索文本，统一归一化方式，记录模型版本。不要复制旧例子里的 1536 维配置。首次写入和查询必须使用同一模型、同一维度；模型变更后重建索引。该适配函数属于待开发内容。

**验收：写入一条记忆，退出 Python 进程，再启动新进程读取；数据库容器重启后仍可读取。** 单纯在同一进程里连问两次，不足以验证持久保存。

## 7. 准备数据：分成三条实验线

### 7.1 LongMemEval：先测记忆是否可靠

使用官方 cleaned 数据。先取小样本验证程序，再扩大，不必第一天跑完 500 题。[数据说明](https://github.com/xiaowu0162/LongMemEval)、[官方下载页](https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned)

以下下载片段会固定数据仓库当前版本，并生成文件校验值：

```bash
uv run python - <<'PY'
from pathlib import Path
import hashlib
import json
from huggingface_hub import HfApi, hf_hub_download

repo = 'xiaowu0162/longmemeval-cleaned'
revision = HfApi().dataset_info(repo).sha
records = []
for name in ['longmemeval_s_cleaned.json', 'longmemeval_oracle.json']:
    target = hf_hub_download(
        repo_id=repo, repo_type='dataset', revision=revision,
        filename=name, local_dir='data/raw/longmemeval',
    )
    records.append({
        'file': name, 'revision': revision,
        'sha256': hashlib.sha256(Path(target).read_bytes()).hexdigest(),
    })
Path('data/raw/longmemeval/manifest.json').write_text(
    json.dumps(records, indent=2), encoding='utf-8',
)
PY
```

将输入分成两个对象：

- **Agent 可见输入**：带时间的历史消息，以及回答阶段才提供的当前问题和问题日期。
- **评分器专用对象**：标准答案、证据会话编号、`has_answer` 等标注。

写记忆时不能看到未来测试问题；模型输入必须剥离 `has_answer`。`oracle` 文件只包含答案证据会话，用来诊断“如果检索完全正确能做到多好”，或者给评分器读取参考答案，不能当普通检索实验的历史输入。

每道题或独立历史建立隔离的记忆空间。若多题共享同一历史，可在同一方法内复用预先构建的只读记忆，但不能把上一题的标准答案或评分反馈写回。

先做历史内容哈希和来源检查，将共享或高度重合的历史放进同一数据组，再划分开发与封存测试清单。建议目标约 100 题开发、其余封存；若分组导致数量变化，以实际清单为准。这是本项目自行划分，不是官方的训练/测试划分。

### 7.2 MemoryArena：再测记忆能否改善任务

官方行程子集是 `ZexueHe/memoryarena` 下的 `group_travel_planner`。它让后续参与者的任务依赖前面已有计划，适合验证跨会话执行。[任务页](https://memoryarena.github.io/)、[运行说明](https://github.com/ZexueHe/MemoryArena/blob/main/setup_travel.md)

它与中文演示不同：官方任务主要测多人计划的衔接，不保证覆盖你设计的所有预算修改或偏好撤回情形。因此：

- 公开任务用于端到端比较。
- 中文自建任务专门覆盖修改、撤销、历史追溯等产品行为。
- 两者的得分分开报告。

先按完整旅行组划分，例如取约 20 组开发、50 组封存验证，其他组暂不使用；不能把同一旅行组的不同参与者分到不同集合。正式数据量以固定清单为准。

“基础参与者的既定计划”是该任务允许的背景输入；后续参与者的 `answers` 属于评分器，不能让 Agent 提前看到。

### 7.3 中文演示集：验证产品行为

建议先做 30 个完整多会话案例：

| 类型 | 建议数量 | 重点 |
|---|---:|---|
| 信息修改 | 6 | 同一行程的预算、日期改变 |
| 多人约束 | 6 | 区分谁的偏好，以及共同约束 |
| 历史查询 | 6 | 原始要求和变更原因 |
| 信息不足 | 4 | 不瞎猜、不编造来源 |
| 撤销与删除 | 4 | 不再使用已撤回的信息 |
| 重启与隔离 | 4 | 重启后可恢复，不串到另一位用户 |

其中约 20 个用于开发，另外 10 个冻结用于演示前回归。合成案例和人工编写案例注明来源，不能包装成真实用户数据。

如需专门增加冲突更新压力测试，再加入 [MemoryAgentBench 的 FactConsolidation](https://huggingface.co/datasets/ai-hyz/MemoryAgentBench)。第一轮不必同时接入所有数据集。

## 8. 开发记忆：先保留依据，再处理更新

### 8.1 三种内容分开保存

| 内容 | 保存什么 | 为什么分开 |
|---|---|---|
| 原始记录 | 用户消息、助手回复、工具返回及时间 | 出问题时能回到原文 |
| 事实版本 | 预算、偏好、人员、日期等可查询字段 | 快速查当前要求和过去要求 |
| 任务结果 | 已生成或已确认的行程、操作状态 | 区分用户要求、助手建议与确认结果 |

助手提出“建议住 A 酒店”，不能自动记成“用户喜欢 A 酒店”。标记来源角色及状态，例如 `proposed`（建议）、`confirmed`（已确认）、`tool_observed`（工具实际返回）。

LongMemEval 也有专门询问助手过去说过什么的题目，因此不能简单删除助手消息；应保留消息角色，在查询时分清“谁说过什么”和“事实是否已被确认”。

### 8.2 最小数据结构

建议先实现以下五张业务表，LangGraph 自己的表交给库管理：

| 表 | 最小内容 |
|---|---|
| `source_events` | 原文编号、实验/用户/旅行/会话编号、角色、消息时间、原文、内容哈希 |
| `fact_versions` | 事实编号、主体、属性、值、适用范围、生效时间、获知时间、来源编号、替代关系 |
| `plans` | 行程编号、版本、计划内容、相关约束编号、建议或确认状态 |
| `memory_jobs` | 待处理原文编号、抽取/索引状态、重试次数 |
| `run_events` | 本次运行每一步的输入摘要、输出编号、耗时、token 与错误类型 |

原文切片和事实摘要可以通过 LangGraph 的 PostgreSQL Store 做搜索。Store 是检索用的副本，正式事实以业务表为准；每个搜索结果带业务表编号，便于重新索引和删除。

一条事实建议包含：

```yaml
fact_id: fact_002
user_id: user_001
trip_id: trip_demo
subject: trip_demo
attribute: accommodation_budget_per_night
value:
  amount: 700
  currency: CNY
scope: this_trip
valid_from: '2026-10-12T09:00:00+08:00'
known_at: '2026-10-12T09:00:00+08:00'
source_event_ids:
  - session_02_turn_01
supersedes: fact_001
source_kind: user_statement
```

`valid_from` 表示这条信息从什么时候适用，`known_at` 表示系统什么时候得知它。比如用户今天说“下个月预算改为 700”，两个时间就不同。无法明确时间时保留不确定标记，不让模型随意补一个日期。

主体、属性、数值单位和适用范围缺一不可。“整次旅行预算 7000”和“住宿每晚 700”不能互相覆盖；“这次旅行不吃海鲜”和“长期不吃海鲜”也不同。

### 8.3 写入流程

建议先同步处理，确认正确后再优化成后台处理：

```text
接收新消息
  → 原文入库，生成稳定编号
  → LangMem 抽取候选事实
  → 校验来源、时间、数值与范围
  → 查同一主体/属性/范围下已有事实
  → 判断补充、替代或冲突待确认
  → 保存新版本和来源关系
  → 更新可搜索副本
  → 标记本次记忆准备完成
```

复用 `create_memory_manager` 的结构化抽取能力，给它明确的字段定义，拿到候选结果后自己保存。这个入口与直接管理 Store 的入口分开，适合保留对写入规则的控制。[LangMem API](https://langchain-ai.github.io/langmem/reference/memory/)

第一版抽取时可以不让 LangMem直接覆盖旧条目；更新决定放在 `temporal.py` 中，避免“库已经改过一次、自己的逻辑又改一次”。所有候选必须绑定到实际存在的来源消息，模型生成的来源编号不直接采信。

重复消息通过原文编号与处理版本防止重复写入。若抽取失败，保留原文并记录任务状态；不要把“暂时没抽出来”当成“没有这项要求”。

### 8.4 更新和历史查询的规则

| 情况 | 处理 |
|---|---|
| 用户明确说“改为” | 相同事项与范围下新增版本，关联被替代版本 |
| 用户说“下次旅行改为” | 建立未来或另一旅行的事实，不影响当前旅行 |
| 两位参与者偏好不同 | 分别保存，计划阶段处理共同安排 |
| 新信息含糊 | 保留冲突标记，必要时询问 |
| 助手自己提出建议 | 存为建议，不改变用户已确认要求 |
| 用户问过去某个时间 | 根据时间及版本记录计算，不能只读当前有效行 |
| 用户撤回要求 | 保留撤回事件，当前查询不再使用旧要求 |
| 用户要求删除信息 | 清理原文、事实、索引、摘要和相关缓存，并测试是否仍能检索到 |

历史查询尤其要注意：如果表里有“当前有效”快捷标记，查询过去时不能直接按它过滤。应按查询时间重放版本，或实现相应的历史查询函数。

这里的来源和时间约束同样用于避免未来信息混入：问题日期之前不知道的内容，不能用于回答当时的问题。

### 8.5 记忆模块的验收

至少覆盖以下用例，检查数据库状态和检索结果，不仅看自然语言回复：

- 500 改为 700 后，当前是 700，历史可查到 500。
- 本次预算改变，不影响另一旅行。
- 同一条消息重放两次，不产生重复版本。
- 助手建议不会覆盖用户事实。
- 时间不明确时不伪造时间。
- 重启后版本和来源仍可读取。
- 用户 A 的记忆不会进入用户 B 的查询。
- 删除后，原文片段和摘要均不能再次被检索。

## 9. 开发上下文：决定每次让模型看什么

### 9.1 先做透明规则

第一版不训练一个复杂的“选择模型”。先实现能解释的规则，并把选择记录下来：

1. 确认当前用户、旅行、会话及允许读取的范围。
2. 当前消息中的明确变更，先进入当前有效要求；不要等旧记忆检索结束才生效。
3. 从事实表读取本次任务必须遵守的当前约束。
4. 用关键词与语义两种方式查相关证据。
5. 去重，并按相关程度、时间、来源可靠性选择。
6. 处理长度上限，给生成模型发送最终上下文。
7. 证据不足时，允许一次进一步查找；仍不足则说明不确定。

旅行组内可共享的行程和参与者个人信息分别标记范围。检索先过滤权限与实验空间，再按相似程度排序；不能先搜所有用户，再靠提示词要求模型忽略。

关键词匹配可以先使用 PostgreSQL 文本搜索或简单词项检索，英文公开数据更容易先跑通。中文关键词需要另做分词或名称匹配；不能宣称英文分词默认就适合中文。

两条检索结果合并时可以按各自排名轮流选取，或使用 RRF（按排名合并结果的一种常见方法），无需先调复杂权重。重新排序模型留作后期实验。

### 9.2 输入长度预算

建议先设模型单次输入上限为 8192 token，并另外预留约 2048 token 输出。实际模型窗口必须能容纳输入、输出和协议开销；以所用模型的计算方法重新检查。

一种初始分配如下，仅作可调起点：

| 内容 | token 上限 |
|---|---:|
| 系统规则和工具说明 | 1500 |
| 当前任务 | 1000 |
| 当前有效约束 | 1500 |
| 历史原文证据 | 2500 |
| 最近对话及工具结果 | 1200 |
| 误差余量 | 492 |
| 合计 | 8192 |

这些是上限分配，不要求每一块填满。某块用不完，可以让给证据；最新明确要求、涉及操作的关键字段不能为了凑预算被截掉。

若当前任务和必须约束已经超出容量，缩小任务或要求补充整理，不悄悄丢弃约束。工具返回过长时，保存完整结果，只把摘要和原文编号放进当前上下文。

每轮工具调用后重新检查长度。裁剪会话时保留工具调用和对应返回的完整配对，避免向模型发送格式损坏的历史。

### 9.3 原文、摘要和证据如何组合

- 原文是判断事实和核对来源的依据。
- 摘要帮助快速了解背景，但要带来源和覆盖范围。
- 当前约束用于决定现在该怎么做。
- 历史版本用于解释以前是什么、为何变化。
- 不让每条摘要都无限复制进下一条摘要。

提供一个 `read_evidence` 工具，输入来源编号才能展开原文。第一轮先给短证据，模型确实需要更多细节时再读取。对比实验要统计这类额外工具调用及其成本。

无需要求模型输出内部思考过程。执行记录保存它实际调用了什么、看到什么依据、做出了什么结果，足以做失败分析。

### 9.4 需要保存的上下文记录

每次模型调用保存：

```yaml
run_id: run_001
case_id: case_001
method: temporal_memory
context_budget: 8192
selected_fact_ids:
  - fact_002
selected_source_ids:
  - session_02_turn_01
dropped_items:
  - id: source_043
    reason: lower_priority_over_budget
input_token_estimate: 4360
prompt_version: context_v1
```

模型响应后补上实际 token 用量、调用耗时、工具次数。估算值和服务端实际用量分开记录；模型隐藏的缓存行为也应记录，而非假设完全没有。

**验收：相同记忆状态、相同查询和配置能生成相同的证据选择；输入不超预算；能够解释每项内容为什么被放入或排除。** 生成文本本身仍可能有波动。

## 10. 接入工具与任务执行

### 10.1 修改现有流程

在模板上增加下面的流程，不重新实现一套 Agent 框架：

```text
接收当前请求
  → 保存当前输入与必要变更
  → 读取记忆
  → 组装上下文
  → 调用模型
      → 如需工具：执行工具 → 保存结果 → 重新组装上下文 → 调用模型
      → 如已完成：检查输出和约束
  → 保存计划版本与运行记录
  → 返回结果和来源
```

`graph.py` 负责流程，数据库细节在 `repository.py`，策略在各自模块里。这样出错时能够定位到一段明确代码。

检查点用于恢复当前运行；长期记忆按 `user_id/trip_id` 等范围存储。测试跨会话时使用新的 `thread_id`，同时保留同一用户及旅行范围，防止实际上一直在用同一条长聊天。

检查点不会自动保证工具只执行一次。保存计划使用稳定的操作编号和版本检查；恢复运行时先确认是否已经保存过。

### 10.2 复用旅行查询工具

优先参考 MIT 授权的 TravelPlanner 的 `tools/` 目录，抽出查询适配层，保留版权和修改记录。它有航班、住宿、餐厅、景点及距离等工具。[TravelPlanner 源码](https://github.com/OSU-NLP-Group/TravelPlanner)

第一版只接三个：

| 项目工具名，待开发 | 作用 | 输出要求 |
|---|---|---|
| `search_transport` | 查某天两地之间的交通 | 稳定编号、日期、价格、时间 |
| `search_accommodation` | 查某城市的住宿 | 稳定编号、价格、人数与规则 |
| `search_restaurant` | 查餐厅 | 稳定编号、地点、餐食类型 |

再补两个自己的业务工具：

- `read_plan`：按旅行编号、版本读取已保存计划。
- `save_plan`：按预期旧版本写入新版本，并返回确切版本号。

工具表中的名称是本项目设计，不是声称上游存在这些同名函数。你需要在 `travel_adapter.py` 中完成映射。

本地数据是实验用的历史数据库，不能当成实时价格。中文演示可用一套小型虚构记录；公开评测使用其要求的原始环境数据，两种结果不混用。

### 10.3 计划检查

输出先通过结构检查：日期、参与者、地点和项目编号是否完整。然后检查：

- 住宿和餐饮是否符合相关参与者的要求。
- 交通是否衔接、日期是否一致。
- 总费用是否按约定的单位、人数、天数计算。
- 是否保留了用户要求不变的部分。
- 所有实际选择是否来自工具返回，或者明确标为待查询。
- 使用的事实与来源是否属于当前实验和权限范围。

公开数据集评分按官方定义执行。本项目增加的预算等业务检查独立列出，不把新增规则冒充为官方评分。

先限制每个任务最多 12 次模型调用、6 次业务工具调用、180 秒墙钟时间；这些是起始保护值，需要根据开发集调整。正式实验所有方法采用相同限制。超时、格式失败和工具失败都计入结果，不能从分母中删除。

### 10.4 最小演示界面

用 Streamlit 做四块内容：

1. 当前对话和最终计划。
2. 当前有效要求，以及最新变更。
3. 被选中的证据，点击可看原文。
4. 本次运行次数、耗时、token 和错误记录。

可以比较同一个输入在不同方法下的结果，但后台必须使用不同记忆空间，不能让一个方法读到另一个方法生成的内容。

**验收：切换新会话后仍记得本次旅行要求；更改预算后计划使用新预算；界面能展示旧值和来源。**

## 11. 评测：把“看起来有效”变成可核对的结果

### 11.1 先回答三个问题

1. 记忆是否保存和检索正确？
2. 选进上下文的内容，是否帮助模型作出正确判断？
3. 这些能力是否改善最终任务，代价是多少？

记忆问答和任务执行分开评估。LongMemEval 成绩好，不能直接推出行程规划也好；MemoryArena 就是为观察记忆与后续行动的联系而设计的。[MemoryArena 项目说明](https://memoryarena.github.io/)

### 11.2 对照方法

所有方法使用相同的生成模型、题目、允许的背景、工具数据和限制：

| 编号 | 方法 | 具体做法 |
|---|---|---|
| B0 | 无跨会话记忆 | 新会话只保留任务协议允许的当前输入，不读取过去会话 |
| B1 | 最近对话 | 只保留最近的完整消息，超预算就舍弃更早内容 |
| B2 | 滚动摘要 | 保存摘要和少量最近内容，每次按统一规则更新 |
| B3 | 普通检索 | 原始历史分片，按语义相似度选取，固定相同检索模型 |
| B4 | Mem0 | 独立记忆空间，使用它的开源记忆能力 |
| Ours | 时序记忆 + 预算内上下文组装 | 当前约束、历史版本、联合检索和可展开证据 |
| Optional | Hindsight | 时间足够时增加完整记忆系统对照 |
| Reference | 全历史输入 | 模型窗口允许时给全历史，单独报告其预算及成本 |

B0 到 Ours 的“回答阶段输入上限”相同；各方法构建记忆的计算量未必相同，必须另外计费，不能称为总计算量完全相等。

全历史输入是参考项，超过模型窗口时记为不适用，不把静默截断后结果叫全历史。Mem0、Hindsight 自带的额外模型调用、摘要和索引也必须纳入费用；若无法获得完整用量，标为不完整成本，不能据此声称最便宜。

先跑 B1、B2、B3 和 Ours。它们能更清楚地解释自研策略的影响；外部系统至少接入一个后再写完整简历结果。

### 11.3 固定一份实验配置

下面是待实现的配置格式：


`temperature: 0` 和随机种子有助于控制波动，但不能保证所有远程模型严格重复。正式版对主要对照方法做三轮独立运行，报告均值及波动；固定数据清单和各轮编号。

实验编号进入数据库命名空间、缓存键和结果目录。缓存键至少包含输入哈希、模型版本、方法配置、提示词版本及数据版本。不同方法不能共享带策略差异的生成缓存。

### 11.4 LongMemEval 的执行流程

```text
读取一份固定历史
  → 移除答案与证据标签
  → 按时间逐会话构建记忆
  → 等待记忆写入与索引全部完成
  → 锁定本次记忆状态
  → 提供问题和问题日期
  → 得到回答与证据编号
  → 独立评分
  → 保存全部题目的结果，包括失败题
```

主结果采用“构建时不知道测试问题”的设置。可以另做查询引导的记忆方案，但那是另一种实验设置，必须另列。

输出兼容官方评分器的最小格式：

```json
{"question_id": "case_id_from_dataset", "hypothesis": "your_answer"}
```

本项目还要输出包含来源、耗时、用量和错误的完整记录；官方最小文件可以从完整记录导出。

复用上游评分提示词与类别判断规则。已核对的 `evaluate_qa.py` 使用固定的模型别名表，不能随意把任意模型名当成命令行参数；它的实际输出文件名也与 README 中的旧描述有差异。详情见调研附件。[已核对的评分源码](https://github.com/xiaowu0162/LongMemEval/blob/9e0b455f4ef0e2ab8f2e582289761153549043fc/src/evaluation/evaluate_qa.py)

如果使用原脚本：

1. 在单独虚拟环境安装 `requirements-lite.txt`。
2. 先验证其中一个受支持别名仍可访问。
3. 使用“当前 Python 解释器 + 脚本绝对路径 + 受支持别名 + 答案文件 + 参考文件”的参数顺序。
4. 评分器读取参考文件；Agent 不得读取参考对象。
5. 保留脚本、模型别名映射及实际模型版本。

如果旧接口不再可用，移植官方评分提示词到自己的模型适配器，记录改动并人工校准。结果写为“沿用官方规则、使用某评分模型”，不能声称与原论文的评分配置完全相同。

### 11.5 MemoryArena 的接入和复现

先把上游作为独立参考目录运行，不把所有记忆后端的依赖装入主应用。其代码自述为预览版，以下步骤需要小样本验证。

准备顺序：

1. 拉取固定提交 `6cd9de14b71915e39ac742a20dc33785e14b6aab`。
2. 按 `setup_travel.md` 建立单独环境。
3. 下载其缺失的 `clean_Flights_2022.csv`，放入指定目录；其他本地旅行文件按说明核查。
4. 验证只调用一个旅行查询工具成功。
5. 将开发组清单接入运行器，再开始模型调用。

官方已有的启动入口是：

```bash
python env/env_server.py
```

记忆后端需要服务时，在另一个终端运行：

```bash
python memory/server.py
```

配置准备好后运行：

```bash
python run_travel.py --config configs/travel_planner_configs/your_local_config.json
```

`your_local_config.json` 是你需要创建的配置，不能原样运行。配置里显式设置：

- `judgement_mode: none`，让测试时不向 Agent 提供答案或提示。
- 所有调用地址使用 `127.0.0.1` 等可连接地址；`0.0.0.0` 通常用于服务监听，不作为客户端访问地址。
- 每次实验使用独立输出目录和独立记忆编号。
- 模型、步数和预算限制与其他方法一致。

上游默认运行完整集合，并会跳过已有输出文件。先增加“按固定清单选组”的包装运行器；不要把重复运行直接写进旧结果目录。

接入自己的方案时，让所有方法使用相同任务 Agent，只替换记忆读取与写入接口。主应用与上游工具格式的转换放在适配器中，不能一边换记忆、一边换生成模型和任务提示词，再把差异全部归功于记忆。

特别核对四件事：

| 检查项 | 已发现的问题或可能影响 | 本项目的处理 |
|---|---|---|
| 无记忆定义 | 上游 `none` 在该快照中仍传递前面的计划 | 单独命名为上游默认设置；真正 B0 由包装层清除跨会话历史 |
| 评分反馈 | 有 `hint` 和 `answer` 选项 | 主实验使用 `none`，评分反馈不进入记忆 |
| 缺失输出 | 评分按已提交组和参与者遍历，可能遗漏未提交项 | 按预定清单核对完整性，缺失项补失败记录；同时记录上游原始得分 |
| 结果匹配 | 评分包含和参考计划槽位的字符串近似匹配 | 报告为官方槽位指标，另报本项目的业务约束检查 |

官方的 PS、SPS、SR 分别涉及参与者计划、约束槽位和整组通过率，以固定源码定义为准；它们不能直接等同于“所有合理行程都能被认可”。

最后，源码中的评分对象 `answers` 应只交给外部运行器，不传给主应用。合法基础计划与后续标准答案必须区分开。

### 11.6 需要报告哪些指标

| 层面 | 指标 | 怎么算或怎么看 |
|---|---|---|
| 最终回答 | 正确率 | 正确题数 / 固定测试题数；失败和空答案计入分母 |
| 记忆能力 | 更新、时间、跨会话、拒答分项 | 用 LongMemEval 标签分别统计 |
| 检索 | 证据召回率 | 被找到的已标注证据 / 全部已标注证据，仅在标注适用时统计 |
| 来源 | 引用支持率 | 抽样检查带引用的结论是否真被引用原文支持 |
| 任务执行 | PS / SPS / SR | 上游固定评分规则，另加完整性检查 |
| 产品行为 | 中文约束满足率 | 按预先写好的案例规则逐项检查 |
| 成本 | 构建、查询、工具、评分费用 | 分项记录，并给出合计 |
| 速度 | 构建时间、查询 P50/P95、任务总时长 | 构建和在线等待分开计时 |
| 稳定性 | 超时、格式错误、工具错误率 | 每项单列，不能只报告成功请求 |

拒答要同时看两方面：该不知道时是否承认不知道、原本可回答时是否过度拒答。证据标签未必完整，缺少标签的题目不要强行计为召回失败。

成本计算建议：

```text
每次实验总成本
  = 记忆抽取与更新
  + 文本向量生成
  + 回答及规划模型调用
  + 额外检索或综合模型调用
  + 评分模型调用

每个成功任务的执行成本
  = 构建 + 查询 + 工具等执行成本之和
    除以成功任务数
```

评分费用另外列出，因为它不是上线后每次用户请求必需的成本。如果成功数为 0，成功任务单位成本标为无法计算。只有确实复用了同一历史的多次查询，才能按实际查询数摊薄构建费用。

每次报告记录价格来源和日期。采用本地模型时记录运行时长、设备和峰值内存，不把本地计算成本写成零。

### 11.7 找出你的设计究竟贡献了什么

先固定 Ours 的其他设置，每次只关一个功能：

- 关闭时序处理：看旧值是否更容易被误用。
- 关闭当前约束直读：看普通检索是否漏掉关键要求。
- 只用语义检索：看关键词合并是否有收益。
- 关闭预算内选择：在相同上限下按固定排序截取，比较证据利用率。
- 关闭摘要：看它节省的长度是否值得付出的信息损失。

对同一批题做配对比较：哪些题从错变对，哪些从对变错。不要只挑几个成功截图。

小数据集的几道题就能让百分比变化明显。报告题数、正确题数、各轮波动；有条件时按对话/旅行组重采样估算误差范围，避免把一两题变化解释成稳定优势。

### 11.8 失败分析模板

每条失败归到可处理的环节：

| 错误类型 | 判断依据 | 优先修哪里 |
|---|---|---|
| 没记下来 | 原文有要求，事实和索引没有 | 抽取与写入 |
| 记错版本 | 存了信息但当前值/时间不对 | 时间与范围处理 |
| 没找到 | 存储正确，检索结果无证据 | 检索 |
| 选错内容 | 候选里有证据，最终上下文没选 | 上下文组装 |
| 理解错误 | 充分证据已在上下文，回答仍错 | 提示词或模型 |
| 工具失败 | 参数、环境或工具返回错误 | 工具适配 |
| 结果格式错误 | 内容可能合理但无法解析 | 输出格式检查 |
| 评分有争议 | 原文或规则支持答案，评分不认可 | 人工复核与评分规则 |

至少人工复核 30～50 条有代表性的结果，覆盖成功、失败、拒答和临界情况。保存判定标准；人工结论和自动分数不一致时，两者一起记录。[评测工程参考](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

时间只有三周时，保留前四种简单方法、记忆版本、LongMemEval 和中文演示，把完整 MemoryArena、Hindsight 和重新排序模型延后。仍要交付真实对照结果。

### 第一周的具体任务顺序

1. 读懂现有模型—工具循环。
2. 将默认网络搜索替换为可重复的本地测试工具。
3. 把模型、数据版本和运行配置写进日志。
4. 跑通数据库重启存取。
5. 写 LongMemEval 输入转换，明确剥离标签。
6. 实现最近对话与普通检索两个方法。
7. 跑 10 题，检查答案编号、评分编号、失败分母是否一致。
8. 再开始开发更复杂的记忆方案。

这样在设计还比较简单时就有可比较的数字，避免开发到最后才发现数据读错或评分接口不兼容。

## 14. 常见问题与处理顺序

| 现象 | 先检查 |
|---|---|
| 换个会话就忘了 | 是否误把检查点当长期记忆；用户范围是否变了 |
| 重启后丢失 | 是否仍用内存存储；数据库卷是否持久保存 |
| 记住了旧预算 | 是否混淆旅行范围、时间和当前状态 |
| 检索看起来很准但任务不变好 | 当前有效约束是否漏选；生成模型是否已看到证据 |
| 新版本明显变慢 | 是否每次都全量抽取、摘要和重建索引 |
| 加摘要后更差 | 摘要是否漏掉数字、否定、人物和时间 |
| 中文效果比英文差 | 是否使用英文分词；中文演示是否涉及额外难度 |
| 换检索模型后异常 | 向量维度、索引、查询提示格式是否一起更新 |
| MemoryArena 首次报错 | 航班 CSV、独立依赖环境、服务端口是否齐全 |
| 评测分数很高但漏了很多题 | 分母是否只统计有输出项；是否复用旧文件 |
| 打开“无记忆”仍记得历史 | 上游是否继续拼接前面计划；是否清除缓存和检查点 |
| Mem0/Hindsight 结果读取不稳定 | 是否写入尚未完成；是否错误使用固定等待时间 |
| 所有方法都错同一批题 | 数据转换、任务歧义、工具数据和评分规则是否有共同问题 |

记忆系统写入完成应由任务状态、返回值或可验证检索来判断，设置超时。不要照搬某个示例里的固定等待 50 秒作为通用解决方法。
